# Evidence 09 - Cross-Site Request Forgery (After Remediation)

## 1. Remediation Strategy & Secure Code Design
The vulnerability was remediated by implementing cryptographically secure anti-CSRF token verification and synchronizer token validation:
1. **Synchronizer Token Pattern**:
   - Each active session generates a pseudo-random session token via `generateSessionToken()`.
   - The token is placed into legitimate forms via hidden input field: `<input type='hidden' name='user_token' value='...' />` generated by `tokenField()`.
2. **Server-Side Validation**:
   - The backend validates `user_token` against `$_SESSION['session_token']` using DVWA's native `checkToken()`.
   - If missing, mismatched, or empty, the request is immediately halted with an HTTP 302 redirect and an error notification `"CSRF token is incorrect"`.
3. **Token Regeneration**:
   - A fresh session token is generated via `generateSessionToken()` after every state-changing request to prevent replay attacks.
4. **Parameterized Update**:
   - The database update utilizes PDO prepared statements for defense-in-depth against SQL injection.

## 2. Remediated Code (`app/vulnerabilities/csrf/source/low.php`)
```php
<?php

if( isset( $_GET[ 'Change' ] ) ) {
    // Security Control 1: Cryptographic Anti-CSRF Token Validation using checkToken()
    checkToken( $_REQUEST[ 'user_token' ], $_SESSION[ 'session_token' ], 'index.php' );

    $pass_new  = $_GET[ 'password_new' ];
    $pass_conf = $_GET[ 'password_conf' ];

    if( $pass_new == $pass_conf ) {
        // Security Control 2: Parameterized query for database update
        global $db;
        $pass_hash = md5( $pass_new );
        $current_user = dvwaCurrentUser();

        $stmt = $db->prepare( 'UPDATE users SET password = :password WHERE user = :user;' );
        $stmt->bindParam( ':password', $pass_hash, PDO::PARAM_STR );
        $stmt->bindParam( ':user', $current_user, PDO::PARAM_STR );
        $stmt->execute();

        $html .= "<pre>Password Changed.</pre>";
    } else {
        $html .= "<pre>Passwords did not match.</pre>";
    }
}

// Security Control 3: Generate fresh anti-CSRF token bound to current session
generateSessionToken();

?>
```

## 3. Post-Fix Verification: Identical Attack Payload
The exact identical forged GET request used in the pre-fix attack was re-submitted without an anti-CSRF token.

### Verification Results
* **Forged Request (No Token)**:
  `http://127.0.0.1:4280/vulnerabilities/csrf/?password_new=hacked123&password_conf=hacked123&Change=Change`
  * **Result**: HTTP 302 Redirect to `index.php`.
  * **User Notification**: `"CSRF token is incorrect"`. Password was NOT changed.
* **Forged Request (Guessed / Fake Token)**:
  `...&user_token=attacker_guessed_token&Change=Change`
  * **Result**: HTTP 302 Redirect. Action blocked.
* **Legitimate Workflow (Valid Token)**:
  Submitting legitimate request with the valid session token succeeds:
  * **Server Response**: `<pre>Password Changed.</pre>`
